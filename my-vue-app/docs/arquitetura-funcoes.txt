====================================================
Guia muito simples da aplicação (explicado devagar)
====================================================

Este ficheiro é um manual escrito como se estivéssemos a explicar o site a uma criança de 6 anos. Vamos dizer o nome de cada peça, o que esse nome quer dizer e para que serve. Sempre que vires "função" imagina um pequeno robô que faz uma tarefa muito específica quando alguém chama por ele.

----------------------------------------------------
1. Pedaços principais do projeto
----------------------------------------------------

- Pasta src/main.js
  - Nome: "main" quer dizer principal. É o ponto de partida.
  - O que faz: cria a aplicação Vue, liga o Pinia (que guarda estados) e o Router (que muda de página). Depois chama os robôs iniciais de cada store com o método init.

- Pasta src/App.vue
  - Nome: App significa aplicação.
  - O que faz: é a casa grande onde moram a barra de navegação (Navbar), o espaço onde as páginas aparecem (<router-view/>) e o rodapé (Footer).

- Pasta src/router/index.js
  - Nome: router significa "roteador", porque decide para onde ir.
  - O que faz: guarda a lista de caminhos (tipo /habits) e diz que componente abrir para cada um. Também tem um guardião (beforeEach) que pergunta ao auth store se a pessoa pode entrar.

- Pasta src/stores
  - Nome: store significa armazém. Cada ficheiro guarda informação e funções sobre um tema (hábitos, itens, etc.).

- Pasta src/api
  - Nome: API é a porta para falar com o servidor JSON.
  - Aqui ficam as funções get/post/patch (o nome diz o método HTTP) e ficheiros como habits.js que usam essas funções.

- JSON Server (db.json)
  - Nome: JSON porque guarda dados em texto JSON, server porque responde a pedidos.
  - Serve para fingir que temos um backend real.

----------------------------------------------------
2. Como o site arranca (ficheiro src/main.js)
----------------------------------------------------

- Função createApp: vem do Vue e cria a app.
- Função createPinia: cria o armazém global.
- Depois usamos app.use(pinia) e app.use(router). "use" aqui quer dizer "liga isto ao app".
- Importamos as funções useAuthStore, useUserStore, useCharacterStore, useItemStore, useBattleStore. O nome "use" é o padrão do Pinia para dizer "deixa-me usar este store".
- Cada store tem uma função init (nome diz tudo: inicializar). Chamamos todas antes de app.mount('#app'), porque queremos ter os dados prontos quando o ecrã aparecer.

----------------------------------------------------
3. Router explicado (src/router/index.js)
----------------------------------------------------

- createRouter e createWebHistory: criam o motor de rotas.
- routes: é um array. Cada objeto tem "path" (o nome do caminho), "name" (um rótulo), "component" (que ficheiro abrir) e "meta" (regras como requiresAuth).
- beforeEach: é uma função que corre antes de trocar de página. Ela liga-se ao auth store:
  - Se a rota precisa de login (meta.requiresAuth) e não há token, manda para /login.
  - Se a pessoa já está logada e tenta ir para /login ou /register, mandamos de volta para /.
  - Se a rota precisa de admin e a pessoa não é admin, mandamos para /.

4. Stores pinia (explicado função a função)
----------------------------------------------------

----------------------------------------
4.1 Store de autenticação (src/stores/auth.js)
----------------------------------------

Nome do store: useAuthStore (Auth vem de Authentication = autenticação).

Estados principais:
- user: o utilizador atual.
- token: um texto que diz "estou logado".

Computed helpers (são funções com nome bonito que devolvem valores prontos):
- isAuthenticated: devolve true se existe token (nome diz "estou autenticado").
- isAdmin: devolve true se o user tem role admin.

Funções internas:
- clearLocalSessionData()
  - Nome: "limpar dados de sessão locais".
  - Faz: remove entradas antigas do localStorage para evitar dados trocados.

- register({ username, email, password })
  - Nome: registar um novo utilizador.
  - Faz: verifica se já existe esse username/email usando get('/users'). Se estiver livre, chama createUser() para guardar no JSON Server, cria userData inicial, cria personagem "vazia" e depois guarda o token e o utilizador em localStorage. No fim tenta carregar os outros stores para sincronizar tudo.

- login(identifier, password)
  - Nome: entrar na conta.
  - Faz: procura tanto por username como por email. Verifica se a password bate certo. Quando encontra, guarda o token, mete o user no localStorage e carrega hábitos, userData, personagem e itens.

- logout()
  - Nome: sair.
  - Faz: apaga token, limpa utilizador, chama clearLocalSessionData e pede aos outros stores para voltarem ao estado inicial.

- init()
  - Nome: iniciar.
  - Faz: quando a app abre, tenta ler user e token do localStorage para manter a sessão.

----------------------------------------
4.2 Store do utilizador (src/stores/user.js)
----------------------------------------

Estados:
- xp (experiência), level (nível), badges (emblemas), streak (dias seguidos).

Computed:
- levelState: usa getLevelState() para saber quanta XP falta.
- xpForNextLevel, xpIntoCurrentLevel, xpProgress, xpRemainingToNextLevel: os nomes dizem exatamente o que devolvem.

Funções:
- saveState(): guarda xp/level/badges/streak no localStorage.
- recalcLevel(): recalcula o nível com base na XP atual.
- gainXP(amount): soma XP e recalcula nível (nome significa "ganhar XP").
- loseXP(amount): subtrai XP sem deixar ficar negativo.
- checkBadges(): vê se a pessoa merece badges novos.
- updateStreak(days): atualiza o número de dias seguidos completos.
- loadUserData(userId): vai ao endpoint /userData buscar os valores guardados.
- init(): chama recalcLevel e guarda o estado ao arrancar.

----------------------------------------
4.3 Store de hábitos (src/stores/habit.js)
----------------------------------------

Estados:
- habits: lista com todos os hábitos do utilizador. É carregada do localStorage logo no início.

Funções públicas:
- saveHabits(): nome diz "guardar hábitos" no localStorage.
- loadHabits(userId): vai ao servidor buscar /habits do utilizador.
- createHabit(habitData): cria um hábito novo com base nas opções do formulário.
- updateHabit(id, updates): encontra o hábito com aquele id e mistura com os novos dados.
- deleteHabit(id): remove o hábito da lista.
- toggleHabitDone(habitId, date): marca ou desmarca o hábito de um certo dia. Controla progressos parciais (progressLog), atualiza streak, dá XP e chama characterStore.levelUp quando o utilizador sobe de nível.

Funções auxiliares dentro do ficheiro:
- calculateStreak(completedDays): recebe uma lista de datas completas e conta quantos dias seguidos temos.
- normalizeHabit(habit): garante que cada hábito tem estrutura completa (dificuldade, XP, progressLog).
- inferDifficultyFromName(name): tenta adivinhar a dificuldade a partir do nome (ex: "Beber água" -> easy).
- getHabitXpValue(habit): devolve o XP baseado na dificuldade ou no xpValue guardado.
- getProgressForDate(habit, date): lê os pontos feitos naquele dia.
- setProgressForDate(habit, date, count): guarda os pontos daquele dia.
- getGoalCount(habit): devolve a meta mínima (pelo menos 1).

Explicação dos nomes usados no formulário de hábitos:
- baseHabitTemplates: significa "modelos base de hábitos". É uma lista fixa com objetos { name, difficulty }.
- habitNameOptions: começa com os nomes dos templates para preencher o dropdown.
- ensureHabitNameOption(nome): garante que o nome existe na lista ("ensure" = garantir).
- baseCategories: lista de categorias iniciais.
- categoryOptions: cópia viva usada no dropdown.
- ensureCategoryOption(categoria): adiciona categorias novas vindas dos hábitos existentes.

----------------------------------------
4.4 Store da personagem (src/stores/character.js)
----------------------------------------

Estados:
- characterType (tipo de personagem), stats (força, vitalidade, agilidade, inteligência), availablePoints (pontos livres), level, currentUserId, characterRecordId.

Funções auxiliares fora do store:
- normalizeRole(type): transforma nomes como "guerreiro" ou "assassino" no formato usado internamente.
- baseStatsFor(type): devolve o conjunto base de atributos para o tipo indicado.

Funções do store:
- saveState(): guarda tudo no localStorage.
- setFromServer(record, userId): copia os dados vindos do JSON Server para o store.
- persistToServer(): envia os dados atuais para o endpoint /characters (POST ou PATCH conforme exista id).
- createCharacter(type): define o tipo escolhido e aplica os stats base.
- reset(): volta à personagem genérica e limpa IDs.
- addStatPoint(stat): gasta um ponto livre para aumentar str/vit/agi/int.
- levelUp(): aumenta o nível da personagem e dá 3 pontos livres.
- init(): chama saveState para garantir que o localStorage está alinhado.

9. Perguntas prováveis (com respostas completas)
----------------------------------------------------

**Onde é guardada cada informação importante?**  
Habits, XP, personagem, itens e fases residem em duas camadas: (1) `localStorage` para manter o estado offline imediato e (2) JSON Server (db.json exposto via `src/api/client.js`) para simular um backend. Por exemplo, hábitos vivem em `localStorage.habits` e também podem ser recarregados de `/habits`; XP/nivel/badges/streak ficam em `localStorage` e no endpoint `/userData`; personagem em `localStorage.characterType` + `/characters`; inventário e caixas com prefixos `inventory_<user>` etc.; progresso de fases em `localStorage.currentPhase` e `/phases` não existe, por isso usamos apenas localStorage para essa parte.

**Onde é gerada a animação da batalha?**  
Todo o comportamento visual está dentro de [src/components/BattleModal.vue](../src/components/BattleModal.vue). As funções `buildHeroAnimations()` e `buildBossAnimations()` carregam os frames; `playerImageState`/`enemyImageState` e os índices de frame determinam qual sprite aparece; `playAnimationOnce`, `playWalkCycle`, `moveCloserBoth`, `calculateDamage` e `handlePlayerTurn/handleEnemyTurn` executam a lógica. O modal também calcula deslocamentos (`playerPosition`, `enemyPosition`) e controla o log (`battleLog`). Se perguntarem “qual função faz X movimento?”, a resposta é sempre “dentro do BattleModal, na função Y listada acima”.

**Como a música de cada boss é carregada?**  
A tabela `BOSS_MUSIC_TRACKS` em BattleModal liga cada Boss (1–6) a um ID do Freesound. A função `playBattleMusicForBoss(bossKey)` chama `getSoundDetails()` (definido em `src/api/freesound.js`), escolhe o melhor preview (`findBestPreviewUrl`) e cria um objeto `Audio`. Estados `battleMusicLoading`, `battleMusicError` e `battleMusicNowPlaying` mostram feedback. Quando o modal fecha ou muda de boss, `stopBattleMusic()` interrompe e limpa o áudio.

**Onde é calculada a streak diária/XP dos hábitos?**  
O `habitStore` guarda cada hábito com `completedDays` e `progressLog`. A função `toggleHabitDone()` atualiza essas estruturas e chama `calculateStreak()` (mesmo ficheiro) para contar dias consecutivos. Para XP, `getHabitXpValue()` usa `habit.xpValue` ou `DIFFICULTY_XP_MAP`; a mesma `toggleHabitDone()` chama `userStore.gainXP()` ou `loseXP()` e ainda dispara `characterStore.levelUp()` quando o novo nível ultrapassa o antigo.

**Quem atualiza XP, nível e badges do usuário?**  
`useUserStore` contém refs `xp`, `level`, `badges`, `streak`. A função `gainXP(amount)` soma XP e chama `recalcLevel()`, que por sua vez consulta `getLevelState()` e dispara `checkBadges()`. A persistência acontece em `saveState()` (localStorage) e em `/userData` através de `loadUserData(userId)` quando fazemos login ou register.

**Onde os itens são criados, equipados e renderizados?**  
`itemStore.generateItem()` cria loot aleatório (escolhe slot, distribui stats, monta nome e imagem). `equipItem(itemId)` troca o item do inventário para `equippedItems`; `unequipItem(itemId)` faz o oposto. As imagens são definidas por `getItemImage(role, slot, name, rarity)` utilizando os diretórios em `src/imagens/personagens/...`. Em `Inventory.vue`, os componentes `EquipmentSlot` mostram essas peças; o boneco central usa `characterSprite` (computed em Inventory.vue) com base no tipo de personagem guardado no `characterStore`.

**Como o progresso das fases é protegido?**  
`battleStore.currentPhase` e `battleStore.phases` são refs espelhadas em localStorage. `initPhases()` define as fases padrão caso esteja vazio. `processBattleResult()` avança a fase, gera o item da recompensa e adiciona caixas com `itemStore.addBox()`. Assim, mesmo sem backend real, a app mantém o estado do utilizador localmente.

**Perguntas de backend comuns durante Q&A**  
- *“Se não têm backend, onde vão as requisições?”* → JSON Server (db.json). Todas as chamadas HTTP passam por `src/api/client.js`. 
- *“Onde está a autenticação?”* → `useAuthStore`. `login()`/`register()` consultam `/users`, guardam `token` em localStorage e o router (`router.beforeEach`) usa `authStore.isAuthenticated` para proteger rotas.
- *“Como fariam a migração para um backend real?”* → basta trocar `BASE_URL` em `src/api/client.js` e manter as mesmas funções (`habitStore.loadHabits`, `userStore.loadUserData`, etc.), porque todo o código front já depende apenas dessas abstrações.

10. Guia simples de variáveis por store (explicações longas)
----------------------------------------------------

### useAuthStore (ficheiro src/stores/auth.js)
- `user`: objeto completo do utilizador atual. Guardado em memória e em `localStorage.user`. Serve para mostrar username, role e ID para outras stores.
- `token`: string (`mock-token-<id>`) que simula sessão. Guarda-se em `localStorage.token`. `isAuthenticated` e `router.beforeEach` só dependem deste valor.
- `register()`: cria user em `/users`, grava registos base (`/userData`, `/characters`), liga os stores (`habitStore.loadHabits`, `userStore.loadUserData`, etc.) e liga o inventário ao novo utilizador (`itemStore.setActiveUser`).
- `login()`: procura por username/email, valida password, grava token/user e recarrega hábitos, XP, personagem, inventário e caixas.
- `logout()`: zera `user/token`, chama `clearLocalSessionData()` para limpar localStorage e tenta reiniciar todos os stores para evitar dados antigos.
- `clearLocalSessionData()`: lista explícita de chaves que são removidas (xp, level, badges, streak, habits, characterType, stats, inventory, etc.).

### useHabitStore (ficheiro src/stores/habit.js)
- `habits`: array com todos os hábitos. Cada objeto inclui `id`, `name`, `category`, `frequency`, `goalCount`, `completedDays`, `progressLog`, `streak`, `xpEarned`, `active`, `difficulty`, `xpValue`. Persistido em `localStorage.habits`.
- `createHabit()`/`updateHabit()`/`deleteHabit()`: manipulam esse array e chamam `saveHabits()` (que escreve no localStorage).
- `toggleHabitDone(habitId, date)`: ponto central para perguntas sobre progresso. Atualiza `progressLog[date]`, marca `completedDays`, recalcula `streak`, atribui XP ao user e dispara `characterStore.levelUp()` se necessário.
- Helpers como `calculateStreak()`, `getHabitXpValue()`, `getGoalCount()`, `getProgressForDate()` explicam “onde” cada cálculo acontece.

### useUserStore (ficheiro src/stores/user.js)
- `xp`, `level`, `badges`, `streak`: cada um está num `ref` e é espelhado nos pares `localStorage` (`xp`, `level`, `badges`, `streak`).
- `gainXP()` e `loseXP()` alteram `xp`, chamam `recalcLevel()` (que usa `getLevelState`) e `saveState()` para persistir.
- `checkBadges()` adiciona `primeiro-passo` e `mestre` quando níveis 1 e 10 são atingidos, respectivamente.
- `loadUserData(userId)`: busca `/userData?userId=...` e substitui `xp/level/badges/streak` para manter o mock server sincronizado.

### useCharacterStore (ficheiro src/stores/character.js)
- `characterType`: string (“warrior”, “mage”, etc.) guardada em `localStorage.characterType`.
- `stats`: objeto `{ str, vit, agi, int }` com os valores atuais. Cada stat também fica salvo em chaves separadas (`stat_str`, `stat_vit`, ...).
- `availablePoints`: quantos pontos de atributo ainda posso gastar (localStorage `availablePoints`).
- `level`: nível da personagem (não o mesmo do user, mas relacionado; guardado em `localStorage.characterLevel`).
- `currentUserId`/`characterRecordId`: permitem relacionar os dados com `/characters`. Quando existem, `persistToServer()` faz PATCH; caso contrário, faz POST.
- Funções importantes: `createCharacter()` (define tipo base), `addStatPoint()`, `levelUp()`, `setFromServer()`, `persistToServer()`, `reset()`.

### useItemStore (ficheiro src/stores/items.js)
- `activeUserId`: quais dados carregar. Guardado em `localStorage.inventory_owner`.
- `inventory`, `equippedItems`, `lootBoxes`: arrays/objetos carregados via `loadState()` usando chaves com prefixo `inventory_<user>`, `equippedItems_<user>`, `lootBoxes_<user>`.
- `generateItem(rarity, role)`: cria um item novo (slot aleatório, stats aleatórios, nome e imagem escolhidos de acordo com `ROLE_SLOT_NAMES` e `getItemImage`).
- `equipItem()`/`unequipItem()`: movem itens entre `inventory` e `equippedItems`.
- `addBox()` e `openBox()`: controlam a quantidade de caixas e chamam `generateItem()` quando abrimos.
- Helpers: `getRarityInfo()`, `resolveSlotName()`, `getSlotName()`, `enrichItem()` (garante que cada item tem imagem e role coerentes).

### useBattleStore (ficheiro src/stores/battle.js)
- `currentPhase`: número inteiro guardado em `localStorage.currentPhase`.
- `phases`: array com os objetos das fases (guardado em `localStorage.phases`).
- `isInBattle`, `battleResult`: apenas em memória para controlar o modal.
- `initPhases()` cria a lista padrão de fases; `saveState()` escreve em localStorage; `calculatePlayerStats()` soma stats da personagem com o bónus dos itens; `processBattleResult()` atualiza fase e chama recompensas.

### BattleModal (ficheiro src/components/BattleModal.vue)
- Variáveis-chave: `playerHP`, `enemyHP`, `playerImageState`, `enemyImageState`, `battleLog`, `battleFinished`, `won`, `boxesGained`, `battleMusicLoading`, `battleMusicNowPlaying`.
- Funções relevantes para perguntas: `startBattle()` (loop principal), `handlePlayerTurn()`/`handleEnemyTurn()`, `calculateDamage()`, `playBattleMusicForBoss()`, `stopBattleMusic()`.

### Inventory.vue e EquipmentSlot.vue
- `characterSprite` (computed) seleciona a imagem baseada na classe do personagem; o sprite fica visualmente dentro da caixa central definida pelo HTML/CSS deste componente.
- `boxCount` mostra o nº de caixas, derivado de `itemStore.lootBoxes.phase1`.
- `EquipmentSlot` padroniza todas as boxes (`w-32 h-32`) e mostra item/imagem se existir.

Essas descrições longas respondem às perguntas típicas (“onde está guardado?”, “qual função gera isto?”, “como sincronizam com o mock backend?”) sem precisar revirar o código durante a apresentação.
----------------------------------------------------

- Quando a app abre, main.js monta tudo e chama init de cada store.
- O auth store decide se alguém pode entrar. Se sim, carrega hábitos, XP, personagem, itens e fases.
- O habit store gere as listas de hábitos e dá XP ao user store, que por sua vez sobe o level e chama o character store para dar pontos.
- O character store soma estatísticas com o item store, e o battle store usa essas forças para simular combates.
- O router garante que cada página abre o componente certo.

Sempre que vires um nome, pensa que ele foi escolhido para dizer exatamente o que faz: save guarda, load carrega, sync sincroniza, init inicia, get devolve, set define. Isto ajuda-te a encontrar rapidamente o robô certo dentro do código.

9. Perguntas rápidas e onde encontrar respostas
----------------------------------------------------


Perguntas sobre Habits (src/views/Habits.vue + src/stores/habit.js):
- Onde adiciono um hábito novo? → Função `saveHabit()` em Habits.vue chama `habitStore.createHabit()`.
- Onde edito ou apago hábitos? → `editHabit()`/`deleteHabit()` em Habits.vue usam `habitStore.updateHabit()` e `habitStore.deleteHabit()`.
- Onde é calculada a streak diária? → `calculateStreak()` e `toggleHabitDone()` no habit store; guardam datas em `progressLog`.
- Onde defino quantos XP cada dificuldade dá? → Constante `DIFFICULTY_XP_MAP` em src/constants/progression.js e helper `getHabitXpValue()`.
- Onde se escolhe a categoria e o nome mostrado no formulário? → Arrays `habitNameOptions` e `categoryOptions` em Habits.vue, alimentados pelas funções `ensureHabitNameOption()` e `ensureCategoryOption()`.

Perguntas sobre progresso e utilizador (src/stores/user.js):
- Quem aumenta o nível quando ganho XP? → `gainXP()` soma a XP, chama `recalcLevel()` e guarda via `saveState()`.
- Onde vejo quanta XP falta para o próximo nível? → Computed `xpRemainingToNextLevel` + `xpProgress`.
- Onde ficam badges e streak geral? → Arrays/valores guardados no user store e sincronizados com `/userData` através de `loadUserData()`.

Perguntas sobre personagem (src/stores/character.js + src/views/Character.vue):
- Onde escolho o tipo (arqueiro, mago, etc.)? → Função `createCharacter(type)` define `characterType` e aplica `baseStatsFor(type)`.
- Onde gasto pontos em STR/VIT/AGI/INT? → `addStatPoint(stat)` diminui `availablePoints` e aumenta o atributo.
- Quem guarda no servidor para não perder a personagem? → `persistToServer()` faz POST/PATCH em `/characters`.
- Onde é mostrado visualmente? → Character.vue lê `characterStore` e mostra stats mais previews dos equipamentos.

Perguntas sobre inventário (src/stores/items.js + src/views/Inventory.vue):
- Onde os itens são criados após a batalha? → `itemStore.generateItem()` chamado dentro de `battleStore.processBattleResult()`.
- Onde guardamos caixas e abrimos loot boxes? → Funções `addBox()` e `openBox()` no item store.
- Onde equipar/desequipar? → `equipItem(itemId)` e `unequipItem(itemId)`, usados pelos botões em Inventory.vue.
- Como a imagem é escolhida? → Helper `getItemImage(role, slot, name, rarity)` monta o caminho correcto.

Perguntas sobre batalhas (src/views/Battle.vue + src/components/BattleModal.vue + src/stores/battle.js):
- Onde é iniciada uma batalha? → Botão em Battle.vue chama `startBattle()` que abre o `BattleModal`.
- Onde correm as fases automáticas e o cálculo de dano? → Dentro do BattleModal (`startBattle`, `handlePlayerTurn`, `handleEnemyTurn`, `calculateDamage`).
- Quem decide quantas caixas ganho? → `boxesGained` definido no BattleModal, enviado para `battleStore.processBattleResult()`.
- Onde se salva o avanço de fase? → `currentPhase`/`phases` guardados via `battleStore.saveState()`.

Perguntas sobre autenticação e routing:
- Onde guardo login e token? → `useAuthStore` (src/stores/auth.js) em `login()` e `register()`, com armazenamento em localStorage.
- Onde verifico permissões ao mudar de página? → `router.beforeEach` em src/router/index.js usa `authStore.isAuthenticated` e `authStore.user.role`.

Perguntas sobre APIs:
- Como falo com o JSON Server? → `src/api/client.js` (`get`, `post`, `patch`, `del`).
- Como falo com a Freesound? → `src/api/freesound.js` (`getSoundDetails`, `searchSounds`, `findBestPreviewUrl`).

Perguntas sobre layout geral:
- Onde estão Navbar e Footer? → `src/components/Navbar.vue` e `src/components/Footer.vue`, incluídos em App.vue.
- Onde cada página é registada? → Na lista `routes` do router; cada entrada aponta para um ficheiro em `src/views`.

Perguntas sobre assets/efeitos visuais:
- Onde ficam as imagens/frames das batalhas? → Pasta `src/imagens/batalha/*`; importadas via `import.meta.glob` em BattleModal.
- Onde ficam os ícones de vitória/derrota? → Mesma pasta, usados no topo do modal.

Com esta secção, cada funcionalidade do site tem uma resposta rápida com o ficheiro e a função responsável. Se precisares de explicar numa apresentação, basta seguir estas perguntas e mencionar os nomes das funções.

Perguntas de backend típicas para a apresentação (8 min demo + 2 min Q&A):
- Como persistem os dados sem um backend real? → Explicar que usamos JSON Server (db.json) como mock; as funções `get/post/patch/del` em `src/api/client.js` fazem pedidos REST e cada store (`habitStore`, `userStore`, etc.) chama os endpoints dedicados (`/habits`, `/userData`, `/characters`).
- Onde está a lógica para sincronizar o front com o “backend”? → Cada store tem um `init()` que lê localStorage e, quando necessário, chama `loadHabits`, `loadUserData`, `persistToServer` (personagem) para alinhar com o JSON Server antes de renderizar.
- Se o avaliador perguntar “onde atualizam XP/stats no servidor?”, responder que `habitStore.toggleHabitDone()` soma XP e depois `userStore.saveState()` guarda localmente, enquanto `userStore.loadUserData()`/`saveState()` empurram para `/userData` no JSON Server; estatísticas da personagem são persistidas através de `characterStore.persistToServer()`.
- Perguntas sobre autenticação (mesmo sem backend real): explicar que `authStore.login()`/`register()` simulam verificação consultando `/users`, emitem um token simples e guardam-no em localStorage; o router usa esse token para proteger rotas (`router.beforeEach`).
- Pergunta “como integram APIs externas?” → Referir `src/api/freesound.js`, que autentica via query token e alimenta o `BattleModal` com `playBattleMusicForBoss`. Explicar que qualquer nova API segue o mesmo padrão (`request helper + store/componente que consome`).
- Pergunta sobre escalabilidade “e quando houver backend real?” → Dizer que basta substituir `BASE_URL` em `src/api/client.js` e apontar os métodos das stores para o novo endpoint, porque toda a app já fala através do client central.

10. Variáveis principais por store/componente (onde vive cada coisa)
----------------------------------------------------

### useAuthStore (src/stores/auth.js)
- **Refs guardadas**: `user` (objeto logado), `token` (string `mock-token-*`). Ambos moram em memória e em `localStorage` (`user`, `token`).
- **Computeds**: `isAuthenticated` (true quando há token), `isAdmin` (verifica role/username).
- **Funções**:
  - `register({ username, email, password })`: cria utilizador via `/users`, registos iniciais em `/userData` e `/characters`, guarda token/localStorage, instancia stores auxiliares.
  - `login(identifier, password)`: consulta `/users` por username/email, confirma password, injeta token/localStorage, carrega hábitos, userData, personagem e inventário.
  - `logout()`: limpa token/user, remove chaves listadas em `clearLocalSessionData`, reinicia os stores (habits, user, character, items, battle).
  - `clearLocalSessionData()`: remove chaves `xp`, `level`, `badges`, `streak`, `habits`, `characterType`, `stat_*`, `availablePoints`, `characterLevel`, `inventory`, `equippedItems`, `lootBoxes`, `currentPhase`, `phases`, `characterUserId`, `characterRecordId`.
  - `init()`: repõe `user` a partir do localStorage se existir token.

### useHabitStore (src/stores/habit.js)
- **Refs guardadas**: `habits` (array normalizado, persistido em `localStorage.habits`).
- **Computeds**: `activeHabits` (filtra `active: true`), `totalHabits` (length).
- **Funções**:
  - `loadHabits(userId)`: chama `/habits` via `fetchHabits`, normaliza e guarda.
  - `createHabit(habitData)`: gera ID com `Date.now()`, cria `progressLog`, `completedDays`, `xpEarned`, `streak` (todos guardados no array), grava.
  - `updateHabit(id, updates)`, `deleteHabit(id)`: editam/removem e persistem.
  - `toggleHabitDone(habitId, date)`: controla progresso diário, atualiza `completedDays`, `progressLog`, recalcula `streak`, dá/retira XP com `userStore.gainXP/loseXP`, e aciona `characterStore.levelUp()` quando necessário.
  - `calculateStreak(completedDays)`, `getHabitXpValue(habit)`, `getGoalCount(habit)`, `getProgressForDate`, `setProgressForDate`, `normalizeHabit`: helpers para responder “onde é calculado X”.
- **Dados**: streaks e logs vivem no próprio objeto do hábito; XP total por hábito fica em `habit.xpEarned`.

### useUserStore (src/stores/user.js)
- **Refs guardadas**: `xp`, `level`, `badges`, `streak` (todos lidos/gravados em localStorage com nomes iguais).
- **Computeds**: `levelState` (usa `getLevelState`), `xpForNextLevel`, `xpIntoCurrentLevel`, `xpProgress`, `xpRemainingToNextLevel`.
- **Funções**:
  - `saveState()`: escreve xp/level/badges/streak.
  - `recalcLevel()`: ajusta nível com base em `levelState` e chama `checkBadges()`.
  - `gainXP(amount)`, `loseXP(amount)`: soma/subtrai XP e chama `recalcLevel` + `saveState`.
  - `checkBadges()`: adiciona badges `primeiro-passo`, `mestre` quando limiares atingidos e devolve os novos.
  - `updateStreak(days)`: usado pelo dashboard/habits.
  - `loadUserData(userId)`: lê `/userData` (JSON Server) e substitui XP/nível/badges/streak locais.
  - `init()`: garante que level está coerente com XP ao carregar.
- **Pergunta “onde está guardado o nível?”** → localStorage `level` + `/userData.level` quando sincronizado.

### useCharacterStore (src/stores/character.js)
- **Refs guardadas**: `characterType`, `stats` (`str`, `vit`, `agi`, `int`), `availablePoints`, `level`, `currentUserId`, `characterRecordId` (todos refletidos em localStorage via `saveState`).
- **Computeds**: `totalStats` (simples soma dos próprios stats; bónus de itens acontece no battle store).
- **Funções**:
  - `createCharacter(type)`: normaliza o papel (via `normalizeRole`), aplica `ROLE_BASE_STATS`, reinicia nível/pontos e chama `persistToServer()`.
  - `addStatPoint(stat)`: verifica `availablePoints`>0, incrementa e sincroniza.
  - `levelUp()`: +1 nível, +3 pontos, salva e sincroniza.
  - `setFromServer(record, userId)`: popula refs a partir de `/characters`.
  - `persistToServer()`: faz PATCH `/characters/:id` ou POST `/characters` com `userId`, stats, pontos, nível.
  - `reset()`: volta ao estado genérico e remove IDs.
  - `init()`: apenas chama `saveState` para garantir localStorage alinhado.
- **Onde vive o sprite escolhido?** → `characterType` + `standardSpriteMap` em Inventory.vue, mas a classe é guardada aqui.

### useItemStore (src/stores/items.js)
- **Refs guardadas**: `activeUserId` (chave para armazenar dados por utilizador), `inventory` (array de itens), `equippedItems`, `lootBoxes` (objeto ex.: `{ phase1: 2 }`). Persistem em localStorage com prefixo `inventory_owner`, `inventory_<user>`, `equippedItems_<user>`, `lootBoxes_<user>`.
- **Funções essenciais**:
  - `loadState()`/`saveState()`: controlam leitura/escrita segregada por utilizador.
  - `setActiveUser(userId)`: troca o dono, recarrega e reprocessa imagens via `enrichItem`.
  - `generateItem(rarity, role)`: cria loot (atribui stats aleatórios, slot aleatório, nome `Slot + tier`, define `role`, imagem e mete no inventário). Responde à pergunta “onde é gerado o item quando ganho a batalha”.
  - `removeItem`, `upgradeItems`, `equipItem`, `unequipItem`: gerem inventário/equipados.
  - `addBox(type, count, max)` e `openBox(type, rarity, role)`: tratam das caixas.
  - Helpers: `getRarityInfo`, `getSlotName`, `resolveSlotName`, `getItemImage`, `enrichItem`, `cleanupLegacySlots`.
- **Dados**: imagens vêm de `src/imagens/personagens/<role>/<slot>/...`; raridade e nomes em `RARITIES`, `ROLE_SLOT_NAMES` no topo do ficheiro.

### useBattleStore (src/stores/battle.js)
- **Refs guardadas**: `currentPhase`, `phases`, `isInBattle`, `battleResult`. Persistem em localStorage (`currentPhase`, `phases`).
- **Constantes**: `fallbackPhase` (usada quando não há fases guardadas).
- **Computeds**: `currentPhaseData` (fase atual), `unlockedPhases` (até `currentPhase`).
- **Funções**:
  - `initPhases()`: cria o array de fases padrão (IDs 1‑7 com HP/Attack/Reward).
  - `saveState()`: grava fase atual/lista.
  - `calculatePlayerStats(characterStore, itemStore)`: soma stats base + itens para gerar `hp`, `attack`, `defense`, `speed` antes do combate.
  - `startBattle()`: marca `isInBattle` true e limpa resultado.
  - `processBattleResult(result, characterStore, itemStore)`: recebe `{ won, boxesGained }`, avança fase, chama `itemStore.generateItem()` e `itemStore.addBox()` quando vitória.
  - `init()`: garante que `phases` existe e grava.
- **Perguntas usuais**: “Onde guardo o progresso das fases?” → `localStorage.currentPhase` + `localStorage.phases`.

### BattleModal (src/components/BattleModal.vue) – principais variáveis para perguntas sobre animação/música
- **Refs**: `playerHP`, `playerMaxHP`, `enemyHP`, `enemyMaxHP`, `playerImageState`, `enemyImageState`, `playerFrameIndex`, `enemyFrameIndex`, `mageEffectFrameIndex`, `playerPosition`, `enemyPosition`, `battleLog`, `battleFinished`, `won`, `boxesGained`.
- **Áudio**: `battleMusicLoading`, `battleMusicError`, `battleMusicNowPlaying`, `battleMusicAudio` (variável local), `trackPreviewCache`. Função `playBattleMusicForBoss(bossKey)` consome `src/api/freesound.js` e usa `BOSS_MUSIC_TRACKS` (IDs 787848, 198841, 563988, 270404, 60013, 270405) para responder “onde está guardada a música do Boss 4”, por exemplo.
- **Helpers de animação**: `buildHeroAnimations`, `buildBossAnimations`, `playAnimationOnce`, `playWalkCycle`, `playMageEffect`, `moveCloserBoth`, `calculateDamage`, `getTurnOrder`, `calculateTurnDelay`, `animateOffset`. Todos vivem neste componente.
- **Estado do turno**: `playerNextActionTime`, `enemyNextActionTime`, `enemyImmobilized`, `distanceUnits`, `playerStepsClosed`, `enemyStepsClosed`.

### Inventory.vue (contexto visual do boneco/slots)
- **Variáveis relevantes**: `characterSprite` (computed sobre `characterStore.characterType`), `typeLabelMap`, `standardSpriteMap` (define imagem por classe), `boxCount` (computed de `itemStore.lootBoxes.phase1`). Slot component `EquipmentSlot` recebe `slot`+`item` e desenha as boxes uniformes.
